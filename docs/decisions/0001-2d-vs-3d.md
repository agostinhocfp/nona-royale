# ADR-0001: Rendering Approach — 2D

> Location in repo: `docs/decisions/0001-2d-vs-3d.md`
> Status: **Accepted**
> Date: 2026-07-10
> Related: `docs/art/ART_DIRECTION.md`, `docs/ART_PIPELINE.md`, ADR-0003 (board topology), `Operator.cs`

## Context

The rendering approach was never formally decided, and the codebase hedged: `Operator.cs` carries both a `SpriteRenderer` and a `MeshRenderer` fallback, and the art notes said "2D" while a later question asked whether the world could be fully 3D-rendered. That ambiguity blocks the art pipeline (paint flats vs. model meshes), the animation pipeline, the Unity architecture, and the file formats. It needed to be pinned before any art or `PathManager` work.

The project is a solo effort by a web developer. The game is a top-down board game; the board is a Ludo/Parcheesi track (ADR-0003); the art bible specifies a stylized look. None of these _need_ real-time 3D.

## Decision

**The game is 2D.** Sprites, painted board, orthographic top-down presentation. This resolves the `SpriteRenderer`/`MeshRenderer` hedge in favor of `SpriteRenderer`; the mesh path is dead.

Rationale:

- The game is designed 2D throughout (top-down board, sprite code, 2D art bible). 3D is not a late rendering toggle — it changes camera, animation, art budget, formats, and architecture.
- A top-down board game gains little from real-time 3D and pays a lot for it (roughly triples art-integration and Unity workload for a solo dev).
- The stated bar is "extremely well done, polished, and runs well." A tight, polished 2D game meets that; a sprawling 3D one risks never shipping.

## 3D is concept-vision only (explicit rule)

3D renders may be produced **solely as concept-vision references** — a one-off "here's the world" beauty shot to align on mood and space. Such renders **never enter the production pipeline** and are never mistaken for a rendering direction. When a vision render is wanted, the cheapest correct path is a 3D-_looking_ painted image from the existing 2D tools (Scenario/Leonardo) using a board schematic as reference — no actual 3D toolchain. A true navigable 3D concept (e.g. Meshy props assembled in Blender) is available but overkill for a static vision shot.

This rule exists so no future session or collaborator reads a vision render as "we render 3D assets."

## 2.5D noted, not adopted

One technique is recorded as available but **not adopted**: modelling assets in 3D (Meshy/Rodin) and rendering them _down_ to 2D sprites from the fixed top-down angle — a standard indie way to get dimensional, richly-lit, consistent characters (including the seated → standing → rise frames) while keeping a 2D game and the existing 2D Unity architecture. If dimensional characters are ever wanted, this is the route — it does **not** reopen the 2D-vs-3D decision, because the _game_ stays 2D; only the art _production_ changes. Adopting it would be its own follow-up ADR.

## Consequences

- Art pipeline targets painted 2D flats and sprites (see `ART_PIPELINE.md`).
- `Operator.cs` and any new rendering code use `SpriteRenderer`; remove the `MeshRenderer` fallback.
- Camera is orthographic top-down.
- If 2.5D is ever adopted, revisit via a new ADR — the 2D game architecture is unaffected either way.

## Later notes

- 2026-09-17: **2.5D adopted for operators** (ADR-0009). Operators are modelled in Meshy and rendered to 2D sprites in Blender. The game stays 2D; the "3D is concept-vision only" rule now has that one exception. Board, environment, UI and FX art are unaffected.
